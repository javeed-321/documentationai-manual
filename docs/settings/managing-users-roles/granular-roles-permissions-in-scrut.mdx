## How User Access Works in Scrut

Every user you add to Scrut gets access in three layers:

- Their **role** determines which modules they can access.
- Their **entity scope** determines which part of your organization's data they can view within those modules.
- Their **permission level** determines exactly what they can do in each module, from read-only visibility to full control.

This three-layered model helps to avoid over-exposing compliance data while keeping day-to-day work easy and manageable for users.

## System Roles

Scrut offers three system-defined roles:

### Admin

Admins have access to every module and nearly every action. The only actions Admins can't take are workflow approvals reserved for a named approver, such as approving a policy, evidence task, risk, mitigation task, corrective action, or access review where the Admin isn't set as the approver. Admins can download and export data from every module.

### Contributor

Contributors get access module-by-module. For most modules, you choose a permission level ranging from no access to full access, and Scrut applies it within the entity or entities the Contributor is scoped to. Contributors don't get access to Dashboard, Reports, or Settings; those stay Admin-only.

### Auditor

Auditors get read-only access, scoped by both entity and framework, unlike Contributors, who are scoped by entity alone. Auditors can download and export data where it's permitted, but can't edit records. Auditors don't get access to Vulnerabilities, Task Center, Integrations, Settings, Trust Vault, Security Questionnaire, Teammates Chat, or Dashboard.

<Callout kind="alert">
  **Note:**

  The Employee role sits outside this access model entirely. Employees can only access the Scrut Employee Portal, where they complete assigned compliance tasks and view relevant policies. They cannot access the Scrut platform (app.scrut.io).
</Callout>

## Entity-Scoped Access

If your organization has multiple entities or business units, you can scope a user's access to one or more specific entities, or give them Org-Wide access.

- A user scoped to a specific entity sees data linked to that entity, plus anything marked Org-Wide.
- A user with Org-Wide access sees data across every entity.

This rule applies everywhere: registers and lists, assignment dropdowns, entity and framework pickers, reports, etc.

## Permission Levels

Most modules use some version of the following levels. Not every module offers every level. Simpler modules like Vault, Employees, and Asset Management use a smaller set, since their data isn't assigned to individual people the way policies, risks, or vendors are.

- **No Access:** The user can't open the module.
- **View Assigned:** The user can view only the items where they're the assignee or approver.
- **View All:** The user can view every item within their assigned entities, but can't edit anything.
- **Edit Assigned:** The user can view and edit only the items assigned to them.
- **View All, Edit Assigned:** The user can view every item within their entities, but can only edit the ones assigned to them.
- **Full Access:** The user can create, edit, and delete every item within their assigned entities.

<Callout kind="alert">
  **Note:**

  Even with edit access, Contributors can't change governance-level fields like an item's name, assignee, approver, or entity. Only Admins and the designated approver can update those fields.
</Callout>

## Download and Export Permissions

Downloading or exporting data is a separate, module-level permission. A user can have full view or edit access to a module and still be unable to export its data unless download permission is also turned on for that module.

## Custom Roles

Scrut also gives you the flexibility to create custom roles with customized module access, permission levels, entity scope, and download permissions.

**Every custom role is built on the Contributor role as its base. Meaning, it’s a contributor role with specific module access, permission levels, entity scope and download permissions.**
